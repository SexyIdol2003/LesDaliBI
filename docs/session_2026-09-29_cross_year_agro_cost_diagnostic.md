## Контекст задачи

KPI 6 должен показывать полную прямую себестоимость на гектар по сезону: агровходы, ГСМ, труд и другие подтверждённые составляющие. В имеющихся витринах часть агрозатрат учитывается по календарному году документа (`season_year` в `mart.v_field_agro_input_cost_direct`), а диагностика объекта затрат содержит `object_harvest_year` и исходный период контура/объекта.

Это потенциально создаёт расхождения между:

- годом документа списания агровхода;
- годом урожая объекта затрат;
- историческим периодом объекта, из которого построена связка.

Важное методологическое ограничение:

> Несовпадение года документа и года урожая объекта не является само по себе основанием переносить сумму между годами KPI.

Даже если дата документа входит в исходный период объекта, это только диагностический признак `CANDIDATE_IN_PERIOD`. Сумма уже присутствует в календарном учёте затрат; механическое добавление её к другому сезону создало бы двойной счёт.

## Исходные витрины и зерно

### `mart.v_field_agro_input_cost_direct`

Используется как источник факта агрозатраты. Для диагностики применялись:

- `document_date` — дата документа;
- `doc_number`, `document_id`, `line_number` — идентификация строки документа;
- `field_name`, `pole_id` — поле;
- `apk_cost_object_key` — объект затрат;
- `nomenklatura_name`, `agro_input_category` — номенклатура и категория;
- `season_year` — календарный год документа;
- `strict_cost_rub_no_vat` — строгая сумма без НДС.

### `mart.v_kpi6_cost_object_diagnostic`

Используется как источник привязки объекта затрат и периода:

- `calendar_year`;
- `pole_id`;
- `cost_object_key`;
- `object_harvest_year`;
- `contour_period_start_source`;
- `contour_period_end_source`.

### Зерно проверки

Зерно итоговой диагностики:

```text
(document_id, line_number)
```

Соединение предварительно дедуплицируется по набору атрибутов объекта (`SELECT DISTINCT`). После соединения рассчитывается `match_rows` на зерне строки документа. Если для одной строки документа найдено более одного соответствия, ей назначается статус `REVIEW_DUPLICATE_JOIN`, а её сумма выводится как неоднозначная и не должна участвовать в контрольной сумме однозначных строк.

На фактическом наборе сессии все строки имели:

```text
match_rows = 1
```

То есть размножения сумм при соединении не обнаружено.

## Интерпретация статусов

| Статус | Значение | Что делать |
|---|---|---|
| `CANDIDATE_IN_PERIOD` | Дата документа находится внутри исходного периода связанного объекта, но год документа и год урожая различаются | Сохранить как кандидат для методологического обсуждения сезонного учёта; не переносить сумму автоматически |
| `REVIEW_OUTSIDE_PERIOD` | Дата документа вне исходного периода объекта | Проверить историческую привязку объекта, контур и источник данных; не относить к году урожая автоматически |
| `REVIEW_REVERSED_PERIOD` | Начало исходного периода позже окончания | Ошибка/аномалия исходной истории объекта; требуется отдельная проверка первичных данных |
| `REVIEW_MISSING_PERIOD` | В объекте отсутствует хотя бы одна граница периода | Неполнота исходных данных; требуется восстановление истории |
| `REVIEW_DUPLICATE_JOIN` | Одна строка документа соединилась с несколькими строками объекта | Не суммировать и не выбирать строку произвольно; сначала устранить неоднозначность связи |

## Принятое решение

1. **Не менять** расчётную витрину KPI 6 и не переносить суммы между календарными/сезонными годами.
2. **Не менять** существующую витрину `mart.v_kpi6_cost_object_diagnostic`, опубликованную отдельным изменением как файл `files/71_mart_kpi6_cost_object_diagnostic.sql`.
3. Хранить `files/72_diagnose_cross_year_agro_cost.sql` как read-only проверку и запускать её перед любыми будущими изменениями сезонной методики.
4. Рассматривать 225 000,00 ₽ только как диагностические кандидаты:
   - 180 000,00 ₽ — семена «Любаша РС1», поле 383.1, документ 2022 года, объект урожая 2023;
   - 45 000,00 ₽ — «Удобрение Стерня-12», поле 999, документ 2021 года, объект урожая 2022.
5. Отдельно расследовать 45 899,24 ₽ по невалидным/неподходящим историческим периодам.

## SQL-файл 72

Файл `files/72_diagnose_cross_year_agro_cost.sql`:

- выполняет только `SELECT`;
- не содержит DDL/DML;
- читает `mart.v_field_agro_input_cost_direct` и `mart.v_kpi6_cost_object_diagnostic`;
- возвращает построчный результат с `match_rows`, суммой `unambiguous_rub` и `diagnostic_status`;
- исключает неоднозначные строки из `unambiguous_rub`;
- не создаёт новую витрину, не изменяет права и не обновляет materialized views.

Пример запуска:

```bash
docker exec -i ldali-postgres-dwh \
  psql -X -v ON_ERROR_STOP=1 -P pager=off \
  -U ldali_admin -d ldali_dwh \
  < files/72_diagnose_cross_year_agro_cost.sql
```

Фактический запуск в сессии вернул пять строк из таблицы выше; все имели `match_rows = 1`.
