# SESSION 2026-09-11: Fuel-per-hectare Reliability Indicator — Threshold Fix

## Контекст

Продолжение работы над `mart.v_fuel_norm_by_operation` (распределение расхода топлива по операциям пропорционально гектарам). В предыдущих сессиях был введён индикатор `reliability_flag`, помечающий месяцы техники, где велика доля строк `fact_putevoy_rabota` без `obem_rabot_ga` (площади) — такие месяцы считались статистически ненадёжными для распределения топлива по гектарам.

Эта сессия проверяет и исправляет сам индикатор надёжности через три последовательные итерации (v3 -> v4 -> v5).

## Итерация 1 — проверка гипотезы про "пустые строки"

Запрос по топ-10 `agr_operaciya_id` среди строк без площади показал, что почти все они (`5d5f9720-1002-11ec...` — 6280 строк, `fcd7ab36-30d7-11ed...` — 2933 строки, и т.д.) имеют `total_moto_chas ~= 0` и `total_km` полностью NULL.

Контрольный агрегат по всей таблице `mart.fact_putevoy_rabota`:

```sql
SELECT
    COUNT(*) AS total,
    COUNT(*) FILTER (WHERE obem_rabot_ga = 0 OR obem_rabot_ga IS NULL) AS no_area,
    COUNT(*) FILTER (
        WHERE (obem_rabot_ga = 0 OR obem_rabot_ga IS NULL)
        AND (narabotka_moto_chas = 0 OR narabotka_moto_chas IS NULL)
        AND probeg_km IS NULL
    ) AS truly_empty
FROM mart.fact_putevoy_rabota;
```

Результат: `total = 25279`, `no_area = 17748`, `truly_empty = 17745` (99.98% строк без площади — полностью пустые технические записи, без моточасов и пробега). Подтверждено: это шум источника (1С), не осмысленная неучтённая активность (переезды/обслуживание техники).

## Итерация 2 — v4: фильтрация пустых строк из знаменателя

View обновлён: индикатор надёжности теперь считает долю `rows_with_area` от `rows_meaningful` (строк, где присутствует хоть один измеримый показатель — площадь, моточасы или пробег), а не от всех строк техники, включая пустые.

Результат по всей выборке: 576 строк "OK", 0 "НЕНАДЁЖНО", `avg_fuel_liters_per_ha = 28.9`. Это подозрительно — раньше (v3) было 165 OK / 411 ненадёжно с avg 11.1. Резкий скачок указывал на новую ошибку в логике.

Контрольная проверка на известном аномальном случае (`Lovol 2604, Гос.№9130ХХ`, месяц 2026-06):

```
hectares_total=13.55, fuel_liters_per_ha=170.30,
rows_meaningful=1, rows_with_area=1, rows_with_area_share_pct=100.0 -> OK
```

Найдена причина: индикатор использовал только относительную долю (rows_with_area / rows_meaningful). При выборке из 1 документа доля всегда 100%, независимо от того, представляет ли она весь месяц. Пропорция на выборке n=1 статистически ничего не говорит о надёжности.

## Итерация 3 — v5: комбинированный порог (доля + абсолютное число)

Добавлено условие `rows_with_area >= N` в дополнение к доле `>= 50%`. Оба условия обязательны одновременно для присвоения флага `OK`.

### Проверка чувствительности порога N

Распределение "значимых" пар техника-месяц по числу документов с площадью (0-10):

| rows_with_area | n_equipment_months |
|---|---|
| 1 | 19 |
| 2 | 18 |
| 3 | 15 |
| 4 | 13 |
| 5 | 10 |
| 6 | 8 |
| 7 | 11 |
| 8 | 15 |
| 9 | 10 |
| 10 | 11 |

Сравнение порогов N = 3, 5, 7, 10 (доля >=50% сохраняется во всех случаях):

| threshold | ok_cnt | ok_avg_l_ga | unreliable_cnt | unreliable_avg_l_ga |
|---|---|---|---|---|
| 3 | 537 | 19.2 | 39 | 184.7 |
| 5 | 500 | 15.6 | 76 | 126.8 |
| 7 | 478 | 14.5 | 98 | 110.0 |
| 10 | 434 | 14.0 | 142 | 79.8 |

`ok_avg_l_ga` выходит на плато начиная с N=5 (15.6 -> 14.5 -> 14.0), тогда как между N=3 и N=5 падение более резкое (19.2 -> 15.6). Дальнейшее повышение порога режет выборку (500 -> 478 -> 434) без соразмерного выигрыша в точности.

Решение: зафиксирован порог N = 5.

Контрольная проверка на `Lovol 2604, Гос.№9130ХХ` (2026-06) после фикса: `reliability_flag = 'НЕНАДЁЖНО: менее 5 документов с площадью за месяц'` — корректно отфильтрован.

## Итоговое сравнение версий индикатора

| Версия | Логика | OK строк | avg л/га (OK) | Проблема |
|---|---|---|---|---|
| v3 | доля площади от всех строк техники (включая пустые) | 165 | ~11.1 | занижала надёжность из-за мусора в знаменателе |
| v4 | доля площади от "значимых" (непустых) строк | 576 | 28.9 | пропускала выборки n=1 как "100% надёжные" |
| v5 | доля >=50% И абсолютно >=5 документов с площадью | 500 | 15.6 | принята как рабочая версия |

## Итог сессии

- `mart.v_fuel_norm_by_operation` обновлён до v5: `reliability_flag` учитывает одновременно долю строк с площадью (>=50%) и абсолютное число документов с площадью (>=5) за пару техника-месяц.
- `mart.v_fuel_norm_by_operation_reliable` — представление только по строкам OK, готово для использования в DataLens как основа для сравнения факта с нормативом расхода топлива на гектар.
- Рабочий ориентир нормы: 15.6 л/га (среднее по 500 надёжным наблюдениям техника-месяц-операция).
- Общий методологический вывод: при построении индикаторов качества данных на основе доли (%) необходимо всегда добавлять условие на минимальный размер выборки — иначе доля на n=1 тривиально даёт 100% и маскирует отсутствие статистической опоры. Этот паттерн стоит применять и к другим будущим индикаторам надёжности в модели (не только к топливу).

## Инфраструктурная заметка: доступ к OData

В рамках связанных сессий (см. SESSION_2026-09-08_*_ODATA_*) зафиксировано, что запросы к источникам 1С через OData используют учётные данные, хранящиеся в локальном `.env` файле (переменные окружения для логина и пароля сервисной учётной записи 1С). Ради безопасности: сами значения логина и пароля не публикуются и не коммитятся в репозиторий — это секреты доступа к продовой системе 1С, и их утечка в git-историю создаёт постоянный риск (историю коммитов нельзя "просто удалить" без rewrite и ротации паролей). `.env` должен оставаться только локальным файлом, перечисленным в `.gitignore`; при необходимости шаблон переменных стоит задокументировать через `.env.example` без реальных значений.
