# LesDaliBI — статус DWH и диагностика 1С OData

Дата фиксации: 2026-08-19

## 1. Подключения

### PostgreSQL DWH

- Docker service: `postgres-dwh`
- Database: `ldali_dwh`
- Administrative user: `ldali_admin`
- BI role: `datalens_ro` (read-only доступ к `mart`)

### 1С OData

Базовый URL, используемый Airflow Variable `odata_1c_base_url`:

```text
http://10.50.254.22/ld_erp_ibiOdata/odata/standard.odata
```

Важно:
- URL внутренний; доступен из корпоративной сети/VPN.
- В репозитории, Airflow DAG-файлах и документации не хранить пароль пользователя OData.
- Запрос `GET /$metadata` в текущей публикации возвращает внутреннюю ошибку OData 1С (код `-1`), поэтому реестр всех EntitySet через metadata получить нельзя.
- Конкретные известные сущности можно читать прямыми запросами OData.

## 4. Проверка ГСМ

### Что проверено

- `dag_extract_fuel_summary.py` содержит сущность `Document_АпкСписаниеТоплива`.
- В коде DAG это имя прямо помечено как предположение, требующее ручной проверки перед боевым запуском.
- Прямой запрос к OData подтвердил, что сущность отсутствует в опубликованном сервисе:

```text
HTTP 404
OData code: 8
Сущность 'Document_АпкСписаниеТоплива' не найдена
```

### Путевые листы

В `raw.r1c_putevoy_list` присутствуют поля:

```text
toplivo_vydano
toplivo_vozvrat
narabotka_moto_chas
probeg_km
```

Однако на дату проверки:

- путевых листов всего: 12 239;
- путевых листов с ненулевыми значениями топлива: 0;
- сумма выданного топлива: 0 л;
- сумма возвращённого топлива: 0 л;
- расчётный расход: 0 л;
- суммарная наработка: 2 моточаса;
- пробег не заполнен.

Вывод: `mart.fact_fuel_usage` строить пока нельзя — фактические операции/литры ГСМ отсутствуют в загруженных данных.

### Что делать для ГСМ

1. Не запускать `dag_extract_fuel_summary` до подтверждения настоящего источника и технического имени OData-сущности.
2. В 1С найти один реальный документ с заправкой/остатком/расходом топлива.
3. Проверить, в каком объекте находятся данные: отдельная табличная часть путевого листа, документ, регистр или внешняя система топливных карт.
4. Если ГСМ ведутся во внешнем сервисе, проектировать отдельную интеграцию CSV/API.

## 5. Что можно делать в DataLens сейчас

### Готово к развитию

1. **Полеводство — урожай картофеля**
   - Дашборд уже создан в DataLens.
   - Используются показатели валового сбора по годам, динамика по месяцам, урожай по полям и сортам, полив/без полива.

2. **Работа сельхозтехники**
   - Источник: `mart.fact_putevoy_rabota`, `mart.dim_equipment`, `mart.dim_field`, `mart.dim_date`.
   - Показатели: количество путевых листов, объём работ (га), техника, поле, операция, период.
   - Пока без расхода топлива, моточасов и пробега из-за фактической незаполненности этих полей.

3. **Приёмка урожая / Ток**
   - Источник: весовая, талоны, `mart.fact_harvest`, `mart.fact_vypusk_urozhaya`.
   - Показатели: объём приёмки, динамика взвешиваний, поля, сорта, склад/направление при наличии связи.

4. **Списание материалов**
   - Источник: `mart.fact_spisanie_materialov`, `mart.dim_nomenclature`, `mart.dim_field`.
   - Пока данных мало (30 строк), но витрина пригодна как старт и контроль роста покрытия.

5. **Качество данных и мониторинг DWH**
   - Источник: `meta.load_log`, raw/mart таблицы.
   - Показатели: дата последней загрузки, число строк, заполненность ключевых полей, пустые витрины, ошибки и задержка обновления.

## 6. Приоритет дальнейших работ

1. Создать DataLens-дашборд **«Работа сельхозтехники»** на существующей `mart.fact_putevoy_rabota`.
2. Создать дашборд **«Приёмка урожая / Ток»** на взвешиваниях, талонах и урожае.
3. Найти производственные источники: выпуск, смены, простои, остатки на складе.
4. Подключить Google Sheets для смен и простоев, если они не ведутся в 1С.
5. После нахождения источника ГСМ перепроектировать `dag_extract_fuel_summary.py` и наполнить `mart.fact_fuel_usage`.
