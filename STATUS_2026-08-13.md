# LesDaliBI — контекст проекта на 2026-08-13

Репозиторий: https://github.com/SexyIdol2003/LesDaliBI
Ветка: `main`
Проект: единая BI/DWH-платформа для ООО «Лесные дали» (агропром, полеводство, производство).

## Архитектура (без изменений с прошлых аудитов)

### Схемы PostgreSQL (`ldali-postgres-dwh`, порт 5432, БД `ldali_dwh`, пользователь `ldali_admin`)
- `raw` — сырые данные из источников (1С OData, Google Sheets).
- `staging` — очищенные и типизированные данные.
- `mart` — витрины для BI / Yandex DataLens.
- `meta` — служебные таблицы и журналы.

### Контейнеры Docker (docker-compose)
- `ldali-postgres-dwh` — PostgreSQL 16, DWH.
- `ldali-postgres-airflow` — PostgreSQL 16, метаданные Airflow.
- `ldali-airflow-web` — Airflow 2.10.3 webserver, порт 8080.
- `ldali-airflow-scheduler` — Airflow 2.10.3 scheduler.

### DAG'и (`files/dags/`)
- `dag_extract_catalogs.py` — загрузка справочников 1С (упаковки, техника, поля).
- `dag_extract_dvizhenie.py` — загрузка документа "Движение продукции и материалов".
- `dag_extract_putevoy_list.py` — загрузка путевых листов тракториста.
- `dag_transform_mart.py` — трансформация raw → mart.

## Источник 1С OData

- Base URL: `http://10.50.254.22/ld_erp_ibiOdata/odata/standard.odata`
- Учётные данные хранятся в **Airflow Variables** (не в коде, не в git):
  - `odata_1c_username`
  - `odata_1c_password`
  - `odata_1c_base_url`
  - `odata_1c_page_size`
  - `dvizhenie_lookback_hours`
- Получить значения: `docker exec -i ldali-airflow-scheduler airflow variables get <имя_переменной>`
- Технический пользователь OData — это НЕ обычный пользователь 1С, а специальный сервисный аккаунт, создаваемый в 1С через **Администрирование → Настройка автоматического REST-сервиса → вкладка "Авторизация"**. Его права на объекты настраиваются НЕ через роли пользователей, а через отдельную вкладку **"Состав"** того же окна (список объектов метаданных, доступных через REST/OData).

## Диагностированная блокирующая проблема (не решена на конец сессии)

### Симптом
Запросы к `Catalog_АпкМоделиСХТехники` и `Catalog_АпкПоля` через OData возвращают:
```json
{
    "odata.error": {
        "code": "20",
        "message": {"lang": "ru", "value": "Доступ запрещён"}
    }
}
```
При этом `Catalog_УпаковкиЕдиницыИзмерения` через тот же логин `OdataBi` отдаёт нормальный JSON с данными — то есть проблема специфична для двух конкретных объектов, а не общая проблема авторизации.

### Что уже проверено и исключено
- Учётные данные (`OdataBi` + пароль) — верны, подтверждены совпадением с Airflow Variables.
- В 1С в окне "Настройка автоматического REST-сервиса → Состав" объекты **"Модели с/х техники"** и **"Поля"** отмечены галочками как включённые в состав сервиса.
- Права обычного пользователя "Бортков Илья Игоревич" (роли "Администратор системы", "Полные права") — не относятся к делу, т.к. `OdataBi` — отдельный сервисный аккаунт со своей независимой моделью прав.

### Дополнительная находка
Запрос к `$metadata` (полный список объектов OData) падает с внутренней ошибкой сервера:
```json
{
    "odata.error": {
        "code": "-1",
        "message": {"lang": "ru", "value": "Произошла внутренняя ошибка OData сервиса. Дополнительные сведения можно найти в технологическом журнале."}
    }
}
```
Это отдельная проблема на уровне сервера 1С (возможно, связана с одним из объектов в составе REST-сервиса, ломающим сборку общей схемы метаданных).

### Не выполненные следующие шаги
1. Посмотреть **Журнал регистрации** в 1С (Администрирование → Журнал регистрации) на события уровня "Ошибка" за время последних тестовых запросов — должен показать точную причину `access denied` и `-1 internal error`.
2. Если есть доступ к серверу 1С — включить/проверить технологический журнал (`logcfg.xml`) для полного стектрейса.
3. Проверить, есть ли в "Состав" REST-сервиса отдельные чекбоксы действий (Чтение/Изменение/Добавление/Удаление) помимо общего включения объекта — возможно, объект включён, но действие "Чтение" не отмечено отдельно.
4. Попробовать снять и заново поставить галочку у "Поля"/"Модели с/х техники" в составе REST-сервиса, сохранить (обязательно кнопкой "Сохранить и закрыть"), и повторно проверить curl.
5. После решения проблемы прав — перезапустить `dag_extract_catalogs`:
   ```bash
   docker exec -i ldali-postgres-airflow psql -U airflow -d airflow -c "DELETE FROM dag_run WHERE dag_id='dag_extract_catalogs';"
   docker compose restart airflow-scheduler
   sleep 20
   docker exec -i ldali-airflow-scheduler airflow dags trigger dag_extract_catalogs
   ```

## Команды диагностики, которые пригодятся в следующий раз

```bash
# Проверить доступ к конкретному справочнику через OData
curl -s -u 'OdataBi:<пароль_из_Airflow_Variables>' \
  'http://10.50.254.22/ld_erp_ibiOdata/odata/standard.odata/Catalog_АпкПоля?$format=json&$top=1' \
  | python3 -m json.tool

# Посмотреть статусы тасков конкретного DAG-рана
docker exec -i ldali-airflow-scheduler airflow tasks states-for-dag-run <dag_id> <execution_date>

# Найти и прочитать лог конкретного таска (в этой версии Airflow нет `airflow tasks logs`)
docker exec -i ldali-airflow-scheduler bash -c \
  'cat $(find /opt/airflow/logs -path "*<dag_id>*<task_id>*" -name "*.log" | tail -1)'

# Получить значение Airflow Variable
docker exec -i ldali-airflow-scheduler airflow variables get odata_1c_username
docker exec -i ldali-airflow-scheduler airflow variables get odata_1c_password
```
