# BI 1С / Лесные Дали — расследование связи "поле ↔ данные" в 1С:ERP АПК

**Дата сессии:** 17 августа 2026
**Продолжение:** SESSION_2026-08-15_BI_1C_AUDIT_AND_ODATA.md

## Цель

После аудита от 15 августа было зафиксировано, что `pole_id` = нулевой GUID во всех фактах (движение, путевые листы, выпуск урожая, списание материалов), а `cost_object_id`/`work_type_id` не заполнены в документах выпуска. Цель этой сессии — вручную обследовать интерфейс 1С:ERP АПК и найти реальный источник связи "поле ↔ документ", а также проверить остальные пустые raw/mart-объекты.

## Главный вывод: как поле кодируется в 1С

Связь с полем **нигде не хранится как отдельный реквизит-GUID** в документах движения/выпуска. Вместо этого используется **текстовое кодирование номера поля** в наименовании нескольких сущностей:

- **Цеховая кладовая** (подтип `Catalog_Склады`, группа «Цеховые кладовые (АПК)»): `318, КаГалаРС2ПУч.6 2025 г. (не исп. с 31.10.2025)`
- **Номенклатура продукции**: `Урожай 2025 ГалаРС3 Белый с поливом., поле 318, уч.6`
- **Подразделение-исполнитель** (в «Этапах производства»): та же кодировка, включая нерабочие состояния поля — `318, Пар 2026 г.`, `868, Заросли 2026 г.`

Расшифровка кода: `{номер_поля}, {культура/сорт}{способ}Уч.{номер}[_{номер_поля}] {год} г. [(не исп. с {дата})]`. Префикс **«Ка»** в культуре = **Капуста** (сорта: Галакси, Алуэтт, Кармен, Ред Леди — реальные сорта капусты, выращиваемые в хозяйстве).

### Проверенные тупики (справочники НЕ содержат структурированной связи)

- Карточка «Цеховой кладовой»: вкладка «Сельское хозяйство» содержит только технические флаги (учёт заправок / весовая / склад подработки) — никакой ссылки на поле.
- Справочник «Партии продукции растениеводства» — в данной инсталляции **отсутствует** (типовой для 1С:ERP АПК 2.5, но не используется в ЛД).
- Подразделение «Поля» в справочнике «Поля» — общее для всех 48 полей, не даёт индивидуальной связи.

### Рабочий способ восстановления связи (подтверждён)

Номер поля в кодированном тексте **точно совпадает** с `Наименование` элемента справочника **«Поля»** (48 полей, например `318`, `751`, `201`, `100`). У каждого поля есть реальный GUID (`raw.r1c_polya`, код вида `AK-00000001`). План парсинга:

```sql
LEFT(text, POSITION(',' IN text) - 1)  -- извлечь номер поля до первой запятой
  = raw.r1c_polya.наименование          -- точное совпадение, JOIN на реальный GUID
```

Для площади/культуры/года — JOIN с `Catalog_АпкПоля_ИсторияПоля` (уже подтверждён в OData: 747 строк истории, 48 полей, 151 культура).

## Реестр обследованных документов 1С — где искать данные

Путь: **Растениеводство → [блок на стартовой странице]**, либо **Растениеводство → Настройки и справочники** для НСИ.

| Документ/справочник | Блок меню | Итог обследования |
|---|---|---|
| **Регистрация взвешиваний на току** | Токовое хозяйство | ✅ Рабочий. Вид взвешивания «Урожай с поля», колонки Откуда (поле+участок+год), Куда (Бункер), Номенклатура, **Вес нетто (кг)** — реалистичные значения (9 900–13 500 кг/ходка). Основной источник `fact_harvest` |
| **Передача продукции из кладовой** | (формируется АРМ выпуска урожая) | ⚠️ Агрегированный документ (периодическая сводка, отсюда аномально большие количества, напр. 455 660 кг) — использовать взвешивания на току как первичный источник, этот документ — как сверочный |
| **Акты на списания семян, удобрений и ядов** | Прочее | ✅ Рабочий. Отправитель = чистое `«Поле {N}»` (без доп. кодировки), Получатель = кодированная партия. Источник для `fact_field_costs` / `raw.r1c_field_writeoff_doc` |
| **Этапы производства** (АРМ по отражению производства продукции растениеводства) | Отражение с/х деятельности в ERP | ✅ Даёт статус по полям/партиям и раскрывает шифр культур (см. выше). Источник для `dim_crop` |
| **Журнал дефектов ТС** | Обслуживание и ремонт ТС | ✅ Рабочий, чистая структура (Техника, Дата, Статус: Устранён/Зарегистрирован/Признан). Поле не требуется. Источник `fact_downtime` |
| **Наработка** | Обслуживание и ремонт ТС | ❌ **Пусто**. Моточасы физически не фиксируются — операционный пробел, не техническая проблема |
| **Заправочные ведомости** | Учёт ГСМ | ⚠️ Есть факт заправки (дата, время, марка топлива, техника, сотрудник), но **нет объёма топлива** в табличной части |
| **Импорты данных по внешним топливным картам** | Учёт ГСМ | ⚠️ Есть объём (литры) и сумма, НО топливо — **бензин АИ-95**, заправки на трассах М5/по Москве и области → это легковой/служебный транспорт, **не сельхозтехника** |
| **Импорты данных по внутренним топливным картам** | Учёт ГСМ | ❌ **Пусто**. Не используется |
| **Списание топлива по суммарной заправке** | Учёт ГСМ | ✅ **Рабочий**. Ежемесячный документ с марта 2023 по июль 2026. Колонки: Техника, Марка топлива (дизель), Заправлено (л), Фактический расход (л), остатки. Даёт расход дизеля **по технике за месяц** — та же техника, что в путевых листах |

## Обновлённая формула расчёта расхода ГСМ на гектар

Прямой связи "топливо ↔ поле" нет ни в одном документе. План расчёта через пропорциональное распределение:

```
расход_на_поле_за_месяц = расход_техники_за_месяц (из "Списание топлива по суммарной заправке")
    × (объём_работ_на_поле_га за месяц / общий_объём_работ_техники_га за месяц)
    [объём работ — из путевых/учётных листов тракториста по той же технике]
```

Точность приблизительная (не учитывает разный расход на разные операции), но это единственный реалистичный вариант без изменения бизнес-процесса.

## Приоритетный план на основе находок

1. Опубликовать в OData/добавить в DAG: `Документ.РегистрацияВзвешиванийНаТоку` (табличная часть с весом нетто), `Документ.АктСписанияСеменУдобренийИЯдов`, `Документ.СписаниеТопливаПоСуммарнойЗаправке`, `Документ.ЭтапыПроизводства`.
2. В `staging` реализовать парсинг номера поля из текстовых полей (склад/номенклатура/подразделение) по правилу "текст до первой запятой" с точным JOIN на `raw.r1c_polya.наименование`.
3. Реализовать пропорциональное распределение ГСМ по полям через связку "Списание топлива по суммарной заправке" ↔ "Путевые/учётные листы тракториста" (по технике и месяцу).
4. Восстановить `raw.r1c_nomenclature` из бэкапа (пункт из аудита 15.08 остаётся в силе).
5. Зафиксировать как officially unsupported: наработка техники (моточасы), расход ГСМ по легковому транспорту в разрезе полей.
6. Согласовать с агрономом/технологом расшифровку кодов культур (`Ка` = капуста + сорт) для построения чистого `dim_crop`.
